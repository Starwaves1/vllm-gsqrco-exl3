## Build: exit 0, both extensions compile real sm75 code
Every unit got `-gencode=arch=compute_75,code=sm_75 -gencode=arch=compute_86,code=sm_86`. The build took 10m47s, with 0 errors and 184 warning lines (`sm75/build-excerpt.txt`). There is no PTX, only SASS.

`cuobjdump --dump-sass` census (`sm75/sass-summary.txt`):

| lib / arch | ELF | kernels | HMMA.1688 | HMMA.16816 | LDGSTS (cp.async) | LDSM | kernels with <= 8 instrs |
|---|---|---|---|---|---|---|---|
| _C_exl3 sm_75 | 61 | 818 | 17184 | 0 | 0 | 1944 | 2 |
| _C_exl3 sm_86 | 61 | 818 | 0 | 8912 | 6992 | 2088 | 0 |
| _C_exl3_mr sm_75 | 17 | 69 | 16128 | 0 | 0 | 1320 | 0 |
| _C_exl3_mr sm_86 | 17 | 69 | 0 | 8064 | 3500 | 1320 | 0 |

The only empty sm75 stubs (`MOV; EXIT`) are `f16acc::rate_kernel<0/1>`. Eight hgemm_f16acc kernels are also compiled without their mma/cp.async on sm75 (568 vs 576 kernels with HMMA). The host keeps that path off on Turing (`hgemm_f16acc.cu`: `if (major < 8) on = 0`), so none of this code runs there. The sm75 build has no trap stubs: the BPT.TRAP counts are about the same on both archs (1560 vs 1548; mr 60 vs 60).

Why it works, checked against the source:
- **m16n8k16:** both the vendored exllamav3 (`csrc/exl3/ptx.cuh`, `arch.cuh`: `EXL3_SM75`) and the trellis-serve Marlin (`third_party/marlin/marlin_mma.h`, `__CUDA_ARCH__ == 750`) issue two fp16 `mma.sync.m16n8k8` per k16 step. This holds for both fp32 and fp16 accumulators, so the `exl3_marlin_h16.patch` fp16-accumulate path also has an sm75 form.
- **cp.async:** replaced on sm75 by synchronous 16 B ld/st; commit/wait become no-ops (`ptx.cuh`, `marlin.cuh` `__CUDA_ARCH__ < 800`).
- **ldmatrix:** used as is (sm75-capable).
- **bf16 mma:** never instantiated. The mr kernel's `a_type` is always kFloat16 (`TRELLIS_KERNEL` in `exl3_marlin_kernels.h`), and bf16 I/O is converted at the Hadamard boundary.
- **Shared memory:** exllamav3 filters shapes at the per-device limit of 64 KB (`DevCtx::get_smem_max`). The mr host code reads `MaxSharedMemoryPerBlockOptin` and raises a TORCH_CHECK if a config does not fit; none did in these tests.

## Multi-row kernel parity (test_exl3_mr.py) and the Turing accumulation fix (session 2, 2026-10-05 11:4x-12:0x UTC)

Run in a copy of the checkout (`/workspace/exl3-sm75b`; the original was serving another agent's 3070 job) with
`get_min_capability` lowered to 75, on the 2080 Ti, `-k "not linear_parts_same_bits and not K5 and not K2"` (the
4B checkpoint has no K2/K5 tensors; 45 deselected).

- **Before** (`sm75/mr-before-patch.txt`): 19 failed, 232 passed, 39 skipped. 15 `test_gemm_vs_fp64` cases over
  exl3_gemm's error x1.5: exl3_gemm_mr rel rms 2.0e-3 to 3.7e-3 against exl3_gemm's 1.1e-3 to 1.9e-3 at 48-384 rows
  (K3-down 384 fp16: 3.34e-3 vs 1.09e-3), plus `test_gemm_mr_multi[48]`. Cause: the vendored Marlin template forces
  `use_fp16_accum` on sm75 for fp16 activations (upstream vLLM's Turing choice: fp16 accumulation over the whole
  k-slice), so every row count accumulated in fp16 without the h16 patch's fold.
- **Fix** (owned patch `csrc/exl3_marlin_h16.patch`): that sm75 block is compiled out, so Turing takes the same
  accumulation as Ampere: fp32, with the h16 fold every 4 k-stages at 9..48 rows. The block is `__CUDA_ARCH__ == 750`
  only, so the sm86 code is unchanged by construction.
- **After** (`sm75/mr-after-patch.txt`): **247 passed, 4 failed, 39 skipped.**
  - `test_draft_head_fp8[1/4/8]`: vLLM's fp8 Marlin refuses bf16 activations on Turing ("Turing only support FP16 or
    INT8 activation"). The test feeds bf16; a Turing server runs `--dtype float16` (vLLM has no bf16 below sm80), where
    the head gets fp16. Not exercised in fp16 on sm75 yet.
  - `test_gemm_vs_fp64[K4-mtp-up-16-bf16model]`: one max-element excess in the h16 (9-16 row) kernel: max_rel 0.0363
    against a bound of 0.0329 (1.5 x exl3_gemm's 0.0219); its rel rms is 2.07e-3 vs exl3_gemm's 1.92e-3 (1.08x). Every
    other row count of that tensor and all K3 cases are inside the bounds.
- `_C_exl3_mr` loads on sm75 and the mr route runs (these tests call it directly).

## Conclusion
The plugin builds for sm75, and the build is real: both `_C_exl3` and `_C_exl3_mr` hold full sm_75 SASS. On sm75 every k16 MMA is two fp16 HMMA.1688, and there is no cp.async or m16n8k16. The only empty sm75 kernels belong to the hgemm_f16acc path, which the host disables below sm80. On the RTX 2080 Ti, the phase-1 kernel suite (`_C_exl3`: exl3_gemm, the reconstruct+hgemm routes, graphs, guards) passes every check that does not need the exllamav3 reference: 346/346, no faults. With Turing's forced fp16 accumulation compiled out of the owned patch, the multi-row kernel passes 247 of 251 (the 4: a bf16-only fp8-head test that cannot run on Turing, and one max-element excess of 1.11x the bound at 16 rows). The plugin's capability gate is now 75. Still open: the decode ladder (the card was lost during server warmup, likely power), dequant bit-exactness against exllamav3.
