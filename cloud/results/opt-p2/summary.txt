Item 1 (fold the MMQ tail memset into the owned quantizer). quantize_mmq_q8_1_x zeroes MMQ's
read tail (J_max + 128 blocks after the quantized data, <= 36 KiB) with a grid-stride loop over
all its threads before quantizing; mul_mat_q no longer calls cudaMemsetAsync. One launch fewer
per MMQ call (360 per step at c=4). Parity unchanged (1970 / 128 skip on, 1939 / 159 off); the
MMQ tests at 1..9 rows run on a poisoned allocator, and the final sanitizer job runs initcheck
without the caching allocator on MMQ at 1/5/8/9 rows, which flags any read of the tail that the
kernel did not write.

Item 2 (IQ1_M, one tensor: blk.13 ffn_gate 17408 x 5120). llama.cpp b11211 has no IQ1_M MMQ
instance (template-instances: iq1_s, not iq1_m), but its MMVQ serves IQ1_M. Microbench
(runs/micro-iq1m-host.txt, us per call in a CUDA graph):
   rows     stock MMVQ  vendored MMVQ (8-row calls)  dequant + x @ W.T  cached bf16 x @ W.T
   1 / 4 / 8   57 / 185 / 406   56 / 87 / 130        505 / 496 / 498    223 / 219 / 222
   16 / 32 / 64      -          259 / 520 / 1034     501 / 562 / 580    224 / 303 / 293
 So: Route L's MMVQ for IQ1_M at any row count up to 32 (8 rows per call above 8, sharing the
 layer's x_q8 in row slices), the stock dequantize + GEMM above 32 (prefill). The cached bf16
 copy would be faster from 16 rows (-0.03 ms at c=4, -0.22 ms at c=8) but costs 178 MB of VRAM
 (~5.6k KV tokens); not taken. Side effect: vLLM's CUDA-graph memory estimate 0.35 -> 0.20 GiB
 (the stock path dequantized the whole weight inside the 9..32-row graph captures), KV cache
 +4.7k tokens (248,437 -> 253,125). Parity 2007 / 146 skip (new: IQ1_M MMVQ at 1..8 rows vs the
 reference models, x_q8, graph replay, q8_1 bytes vs vendored, 8-row chunks with and without
 x_q8 slices; IQ1_M MMQ cases skip), stock 1973 / 180; CPU guards: IQ1_M MMVQ passes the
 guards, IQ1_M MMQ is rejected before any launch ("no MMQ for IQ1_M").

Item 3 (q8_1 quantize fused into its producer): not done. The producers of the quantized X
are vLLM's: RMSNorm (inductor-generated add + norm kernels) for qkv / in_proj_qkvz / gate_up,
act_and_mul (vLLM CUDA op) for down, attention / GDN gated norm for o_proj / out_proj. A fused
norm + q8_1 needs either the model's norm module replaced or an inductor pattern pass registered
in vLLM's pass manager, i.e. vLLM-side changes. Estimate: of 275 quantize launches per c=1 step
(0.41 ms, ~1.5 us each) the ~150-190 whose X comes from an inductor kernel (norms, the attention
gate) could fold into it: ~-0.2 to -0.3 ms at c=1, ~-0.3 ms at c=4 (<= 1%). Expressing q8_1 in torch ops for inductor to fuse is not
bit-exact (roundf vs round-half-even, fast-math division, sum order).

Item 4 (gate_up + silu*mul). The 48 CatArrayBatchedCopy per step are vLLM's GDN core (eager
aten::cat inside qwen_gdn_attention_core; attributed from the trace), not the gate_up path. A
same-type gate/up run is one product and feeds act_and_mul with no cat. Mixed-type fused layers
(gate/up in 40 of 64 blocks, and qkv / in_proj_qkvz) join their runs with inductor's triton cat: 75 launches,
0.12 ms at c=1, 0.17 ms at c=4. Removing it needs the runs' kernels to write into column slices
of one buffer: the vendored MMVQ/MMQ take a dst row stride, but the owned IQ3 / Q4_K / IQ2_S
kernels (K-agent files) write contiguous rows, and hiding the cat in one op undoes the free
split-fold opt-p found for in_proj_qkvz. Skipped.

Item 5 (embedding, lm_head). Host cost per eager call (runs/micro-iq1m-host.txt, 2000 calls):
embedding 35.1 us through the custom op (27.9 calling the Python directly, 20.5 for
index_select + the C++ dequantize alone); GPU 0.02 ms per step. At c=1 the 4 embedding calls
leave the GPU idle for their host time (gaps.py attributes 0.31-0.34 ms/step of profiled idle
to them; the profiler roughly doubles host time), the eager lm_head calls do not (their host
time overlaps GPU work). The removable part is <= 15 us per call (<= 0.06 ms/step, 0.2%): not
worth a change. lm_head: the 248,320-wide fp32 -> bf16 cast in the shim and the sampler's
bf16 -> fp32 cast are ~5 us GPU each per step and off the critical path; returning fp32 logits
(vLLM's head_dtype=float32 path) would drop both but changes greedy tie-breaks: not done.

Item 6 (output casts via inductor fusion), measured and reverted (commits 0255980, 1aaf081).
The shim ops took an optional output dtype, _fused_mul_mat_gguf returned fp32 on Route L
types and apply() cast in the traced graph. Inductor fused the cast into the add + RMSNorm
kernels and the runs' cat (triton_poi_fused__to_copy_cat_*), but where the consumer is a
custom op (act_and_mul, GDN conv) it emitted standalone triton casts, and the add + norm
kernels read fp32. Net -0.12 / -0.19 ms per step at c=1 / c=4, e2e within noise. Against it:
KV cache -3.1k tokens (the runs' fp32 outputs now live until the fused cat), and it is not
bit-exact with the separate cast: inductor keeps a fused bf16 intermediate in fp32
(emulate_precision_casts is off), which its own guard test caught (test_cast_fused_by_inductor
failed on the box). Not a clear win: reverted.

Other plumbing checked (not in the item list):
 - GDN in_proj_ba (BF16 96 x 5120) above 8 rows (runs/micro-ba.txt): F.linear is already the
   fastest of F.linear / batched gemv / K-major mm / fp32-out mm / w @ x.T at 9..32 rows
   (6.0-7.1 us); nothing to take (0.32 ms/step at c=4 is 48 x 6.7 us).
 - Stream-k fixups (325 launches, 1.19 ms at c=4): stream_k is a compile-time field of the
   vendored MMQ config tables (mmq.cuh), not an mmq_args field; no shim knob.
 - Sharing one MMQ-layout quantize among a fused layer's MMQ runs with the same ds layout
   (as opt-p did for MMVQ): ~75 launches, ~0.11 ms at c=4; needs an x_q8 on lcpp_mul_mat_q
   with the zeroed tail. Left: K3's 16-64-row kernels may change which layout those runs read.
