Item 1 (IQ3 kernel output in X's dtype). The owned iq3_mul_mat_vec stores fp16/bf16 (round to
nearest even, as torch's cast) instead of fp32 + a separate cast; vendored MMVQ/MMQ keep theirs.
Per c=1 step: bf16 casts 374 -> 182 launches (0.58 -> 0.27 ms), all GPU activities 2296 -> 2104.
Parity: 1179 pass / 16 skip (new: 16-bit output == fp32 output cast by torch, all IQ3 cases).
GPU guards (once, on this .so): 90 pass / 10 skip (x_q8 cases on MMQ ops), 0 fail.

Item 2 (quantize X once per layer input). apply() quantizes X once (custom op _quantize_x_q8_1)
for all runs of a fused layer that read q8_1 (MMVQ, IQ3 kernel) and passes it as the new optional
x_q8 of lcpp_mul_mat_vec_q / lcpp_mul_mat_vec_iq3; MMQ runs (other layout) quantize for themselves.
Per c=1 step: quantize launches 375 -> 276 (0.52 -> 0.42 ms), GPU activities 2104 -> 2005.
 - First version put the whole run loop and its torch.cat inside one custom op. Not measured:
   in Qwen3.5 GDN the in_proj_qkvz output is split([qkv, z]) right away and inductor folds
   the plugin's cat into that split today (no cat kernel for these layers; the 48 cat launches
   per step in every profile are vLLM's GDN core). Hiding the cat in an op would have added a
   real cat per layer. The kept version leaves the cat in the traced graph: cat launches stay 49.

   and blk.13's gate_up starts with IQ1_M (stock path, not a Route L type). Fixed (first run

apply() stay bit-exact). CPU guards 52 pass. CPU suite on the box: same 370 pass / 84 fail / 10
error as base (all failures need local libggml / llama.cpp fixtures that the box lacks).
