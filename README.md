# vllm-gsqrco-exl3

Two quantization plugins for vLLM, tuned per GPU generation, plus the small upstream fixes found on the way.

- **GSQ-RCO on vLLM.** [GSQ-RCO](https://huggingface.co/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF) (Gumbel-softmax quantization with Riemannian constrained optimization, from ISTA-DASLab) produces GGUF files that mix llama.cpp's IQ2, IQ3 and IQ4 codebook types with K-quants. They are among the best 3-bit weights available for Qwen3.8-27B. Before this repo, vLLM could load them only through the stock GGUF plugin, whose kernels dequantize to bf16 and call cuBLAS above a few rows: 32 tok/s at c=1 on an RTX 3090, a third of what the same card does with a Marlin W4A16 model. After: the plugin vendors llama.cpp's MMVQ and MMQ kernels byte for byte, adds owned int8 tensor-core kernels for the row counts speculative decoding actually produces, repacks IQ3 at load time, and routes every matmul by type, row count and shape. Same model, same card, same vLLM: 110 to 125 tok/s at c=1 with MTP, more context in VRAM than the W4A16 model, and bit-identical results under CUDA-graph replay.
- **EXL3 on vLLM.** [EXL3](https://github.com/turboderp-org/exllamav3) is trellis-coded quantization: instead of rounding each weight to a grid, it encodes a whole block as one path through a trellis whose states are generated by a cheap hash, so every 3.5-bit code picks from a Gaussian-shaped codebook and the encoder (a Viterbi search, run once offline) recovers most of the 0.25 bit per weight that scalar quantization gives away to the sphere-packing bound. Decoding is a handful of integer ops per weight. This repo's second plugin serves EXL3 checkpoints on vLLM with a multi-row kernel for the MTP verify pass, host-pinned embeddings, and an fp8 draft head, and it matches or beats the Marlin W4A16 path per step at c=1, 2 and 8.

Both plugins survived 12-hour torture soaks (45,723 and 36,992 responses, zero faults) on the same card. Validated so far on sm86 (RTX 3090, RTX 3070); the generation table below is how coverage grows.

## Numbers that matter

One RTX 3090 at its stock 350 W limit, Qwen3.8-27B, 200k context budget, fp8 KV, MTP with a fixed k=3, CUDA graphs, pass 2, T=0. Throughput is normalized to the production reference, Qwen3.8-27B W4A16 served by stock vLLM with Marlin and MTP, measured in the same session (97 / 194 / 355 / 509 tok/s at c=1/2/4/8).

| decode, normalized tok/s (W4A16 + MTP = 1.00) | c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|---|
| **GSQ-RCO IQ3_S, this plugin** | **1.29** | **1.13** | **1.08** | **1.20** |
| **EXL3 3.5 bpw, this plugin** | 1.04 | 0.93 | 0.85 | 0.95 |
| W4A16 Marlin on stock vLLM (reference) | 1.00 | 1.00 | 1.00 | 1.00 |
| official INT4 on stock vLLM, no MTP possible | 0.46 | 0.43 | 0.45 | 0.63 |
| GSQ-RCO through the stock GGUF plugin kernels | 0.33 | 0.20 | not run | not run |

| decode, ms per engine step (lower is better) | c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|---|
| GSQ-RCO IQ3_S, this plugin | 26.0 | 29.8 | 33.9 | 42.6 |
| EXL3 3.5 bpw, this plugin | 27.0 | 27.1 | 32.2 | 38.9 |
| W4A16 Marlin (reference) | 26.1 | 26.0 | 29.0 | 40.9 |

Read the two tables together. Tokens per second multiply two things: how fast the engine steps, and how many draft tokens each step accepts. GSQ-RCO's draft head accepts about 3.3 tokens per step, EXL3's about 2.6, W4A16's about 2.6, so the GSQ-RCO lead in tok/s is partly the draft head's and the per-step table is the honest kernel comparison. Per step, both plugins now sit at or near the Marlin reference while streaming 8 to 14% fewer weight bytes; the remaining gap at c=4 is per-byte kernel efficiency at 12 to 48 rows, which is the current optimization target. Prefill with GSQ-RCO is 1.07 to 1.13x the reference at 8k to 180k.

| fit at 200k context | GSQ-RCO | EXL3 | W4A16 | official INT4 |
|---|---|---|---|---|
| weights streamed per step | 11.7 GB | 12.5 GB | 13.6 GB | 15.1 GB |
| KV tokens on the card | 253,906 | ~200,000 | 207,812 | 136,800 |

All raw data, scripts and per-run logs are under `cloud/results/`; the methodology (ms per step, pass-2, floors) is in `STATUS.md`.

## Generations, not cards

Tuning is keyed by GPU generation (compute capability), never by card. Tables ship per generation; several cards of one generation are validation points that must agree, and a disagreement inside a generation is a finding to explain, not a per-card entry. Untested generations get the vendored llama.cpp path by construction.

| generation | cards run | tier 1 (kernels) | tier 2 (4B end to end) | tier 3 (27B) | torture |
|---|---|---|---|---|---|
| sm75 Turing | RTX 2080 Ti | in progress | in progress | n/a (11 GB) | planned |
| sm86 Ampere | RTX 3090, RTX 3070 | 3090 pass; 3070 run, agreement check pending | pending | 3090 done | 3090: both plugins 12 h pass |
| sm89 Ada | RTX 4070 (two) | planned | planned | n/a | planned |
| sm120 Blackwell | RTX 5090 | planned | planned | planned | planned |

Before the optimization work goes upstream, every row above runs the same tagged commit through the kit and the torture harness; that table becomes the PR's evidence.

## How the pieces fit

```
vLLM (main + the Starwaves1/vllm overlay: KV disk tier, vision CPU offload, spec-decode fixes)
 ├─ plugin/         GSQ-RCO GGUF: Route L (vendored llama.cpp kernels) + owned kernels + per-generation dispatch
 ├─ plugin-exl3/    EXL3: vendored exllamav3 kernels + multi-row MTP kernel + host-pinned embedding
 ├─ kit/            validation kit: parity, micro-benchmarks, ladders, per-generation report
 ├─ bench/torture/  12 h torture harness
 ├─ cloud/gq/       cluster job queue across the test machines
 └─ docs/upstream/  one report per upstream contribution, the standard they follow, and the complete bug list
```

One venv holds both plugins; `scripts/serve-gsq.sh` and `scripts/serve-exl3.sh` switch between them.

## Install and build

Requirements: Linux, an sm_86 GPU, a driver that supports CUDA 13, [uv](https://docs.astral.sh/uv/). The CUDA toolkit comes from pip wheels. The build needs no system packages and no sudo.

```sh
git clone https://github.com/Starwaves1/vllm-gsqrco-exl3 && cd vllm-gsqrco-exl3
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r env/prod-freeze.txt    # vLLM 0.27.1, torch 2.13.0 cu130
uv pip install --python .venv/bin/python --no-deps \
  "gguf @ git+https://github.com/ggml-org/llama.cpp@b11211#subdirectory=gguf-py"
tools/setup-cuda-toolchain.sh                   # nvcc 13.0 into build/cu130, matching torch's cudart
VLLM_GGUF_BUILD_LCPP=1 tools/build-plugin.sh    # editable install, sm_86; a few minutes
```

Without `VLLM_GGUF_BUILD_LCPP=1` the build skips Route L and takes about 20 s. `tools/setup-cuda-toolchain.sh` also patches its private CUDA 13.0 header copy on glibc 2.41 or newer.

The published numbers also used a small vLLM 0.27.1 patch set, [Starwaves1/vllm@ba05ffab](https://github.com/Starwaves1/vllm/commit/ba05ffababdcf89ada26b5d34845e04901e2ddf3). It adds size-capped filesystem KV tiers and a row-pruned MTP draft head that reads `mtp_draft_vocab_ids.pt` from the HF config dir. On stock vLLM 0.27.1, set `MTP_DRAFT_VOCAB=0` and use a CPU-only KV tier. That combination was not benchmarked, and KV capacity will differ.

## Run

vLLM needs an HF config dir next to the GGUF. Both tested models have one in `hf-config/`. Check yours against the GGUF with:

```sh
.venv/bin/python tools/make_hf_config.py verify --gguf /models/Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf \
  --out hf-config/Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp \
  --template hf-config/Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp/chat_template.jinja
```

Give every model its own HF config dir. The plugin sets `model_config.model` to that dir, and vLLM's filesystem KV tier namespaces its keys on it, so two models sharing one dir would read each other's KV blocks.

```sh
export VLLM_GGUF_LCPP=1 VLLM_PLUGINS=gguf PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
CFG=hf-config/Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp
.venv/bin/vllm serve /models/Swift-1.5-Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf \
  --hf-config-path $CFG --tokenizer $CFG --served-model-name swift-gsq \
  --gpu-memory-utilization 0.94 --max-model-len 200000 --max-num-seqs 8 \
  --kv-cache-dtype fp8 --mamba-ssm-cache-dtype float16 --mamba-cache-mode align \
  --max-num-batched-tokens 2048 --long-prefill-token-threshold 128 --no-async-scheduling \
  --limit-mm-per-prompt '{"image":0,"video":0}' \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3,"draft_sample_method":"probabilistic"}' \
  --compilation-config '{"max_cudagraph_capture_size":32,"custom_ops":["+rms_norm","+silu_and_mul"]}' \
  --reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder \
  --enable-prefix-caching --enable-cumem-allocator --scheduling-policy priority \
  --kv-offloading-size 16
```

The GGUF has no vision projector, so image and video limits must be 0, or pass `--language-model-only`.

## Tests and harnesses

```sh
tools/pytest tests/cpu                                            # CPU only, never touches the GPU
VLLM_GGUF_LCPP=1 GSQ_ALLOW_GPU=1 GSQ_GGUF=/models/X.gguf tools/pytest tests/gpu -v
```

`tools/pytest` keeps pytest in `build/pytest`, outside the venv. CPU tests import `tools/no_gpu.py` first. The 112 Route L guard tests in `tests/cpu` skip unless the plugin was built with `VLLM_GGUF_BUILD_LCPP=1`. GPU tests skip unless `GSQ_ALLOW_GPU=1`. `tools/capped` is an optional wrapper that caps memory and CPU for builds and tests on a shared host.

The harnesses were written for one setup. Paths and ports are environment overrides in `scripts/env.sh`.

| harness | what |
|---|---|
| `scripts/serve-gsq.sh`, `scripts/serve-baseline.sh` | serve the GGUF or the W4A16 reference on the same argv, from `env/prod-serve-argv.txt` |
| `bench/speed/run.sh` | decode ladder at c=1/2/4/8, salted prefill ladder at 8k/64k/180k, MTP acceptance from `/metrics`, GPU clocks; the decode cohort script it wraps is not public yet |
| `bench/parity/` | llama.cpp b11211 logit dumps vs vLLM logprobs on the same ids, KLD and top-1 per position |
| `bench/micro/gemm.py` | per-op GEMM microbenchmarks |
| `bench/soak.sh`, `bench/soak_load.py` | long soak: mixed chat, tool calls, long prompts up to 120k, aborted streams, random priorities; logs liveness, memory and device faults every 60 s |
| `cloud/bootstrap.sh` | sets up a rented sm_86 box and runs tests, parity, speed and an optional soak |
| `dash/` | optional status page for a rented box: GPU, memory, and a file-based GPU job queue polled over ssh; the box address comes from the gitignored `dash/data/box.json` |
